Pattern Language

風控系統設計原則

本文件記錄了從風控系統重構經驗中提煉的設計原則。共 12 條 pattern，其中 11 條來自自身實踐，1 條來自主管指導。

結構設計層

Pattern 1：分層不等於約束（你的）

分層解決的是「東西放哪裡」，不是「誰可以改什麼」。如果分層後還是要用人腦追蹤狀態變更，代表缺少的是寫入權的設計。

寫入一致性層

Pattern 2：狀態寫入的三原則（你的）

每個可變狀態都有唯一的權威來源。原始資料與衍生資料要區分——衍生狀態只能被計算，不能被直接賦值。所有變更都該能回答「因為什麼事件」。

Pattern 3：一致性有兩層（你的）

寫入權歸屬定義的是「誰能改」，但一致性還需要定義「改的邊界在哪」——哪些變更必須一起生效，中間狀態能不能被觀察到。

讀取一致性層

Pattern 4：寫入與讀取是兩種一致性（你的）

寫入一致性回答「誰能改」，讀取一致性回答「讀者看到的是哪個時間點的世界」。輪詢是一種 trade-off：用即時性換簡單性，前提是業務能接受那個延遲窗口。

Pattern 5：輪詢延遲的疊加（你的）

兩個獨立輪詢的最大延遲是它們週期的總和，不是單一週期。如果 A 每 100ms 寫、B 每 100ms 讀，B 看到的資料最多可能落後將近 200ms。

Pattern 6：場景區分一致性要求（你的）

同一份資料在不同使用場景可以有不同的一致性要求。區分清楚誰需要強一致、誰能接受最終一致，可以避免為了最嚴格的場景把所有場景都做複雜。

容錯設計層

Pattern 7：失敗要明顯（主管的）

當狀態可以透過重算自我修復時，失敗應該產生「明顯錯誤」而不是「貌似正確」——因為明顯錯誤會被下一次正確覆蓋，貌似正確會一直留著。

啟動與恢復層

Pattern 8：就緒依賴而非順序依賴（你的）

啟動順序不等於就緒順序。依賴的不是「對方的進程活著」，而是「對方的狀態可用」。需要有明確的就緒信號，而不是靠時間差假設對方好了。

效能與擴展層

Pattern 9：輪詢週期是意圖不是保證（你的）

輪詢週期的設定只是意圖，實際週期是「處理時間」和「設定週期」取大值。當處理時間超過設定週期，整個時序假設都要重新檢驗。

Pattern 10：分區鍵要和聚合維度對齊（你的）

分區的維度應該和最終聚合的維度對齊。如果分區鍵和聚合鍵不同，分區帶來的並行性會被跨區查詢吃掉。

Pattern 11：分區是複雜度換吞吐量（你的）

分區解決的是單點處理能力的上限，但會把原本不存在的「協調」和「容錯」問題引進來。分區不是免費的並行，是用複雜度換吞吐量。

Pattern 12：封閉分區是最乾淨的分區（你的）

當處理邏輯和聚合邏輯都能封閉在同一個分區鍵內，分區就是單純的水平擴展，不需要引入分散式協調。

這些 pattern 有一個隱含的順序：結構設計是前提認知，寫入與讀取一致性是核心設計，容錯與啟動是邊界處理，效能與擴展是規模應對。

對軟體設計的反思
對軟體設計的反思為什麼這麼多人體認到設計是再指邊界的事，大家或是一些感覺很厲害的人(我主管、這個做PPT的人、一些軟體大師)都不約而同指出，設計、邊界、職責等這類能夠幫助我們在設計更好的往前走的部分。 但我想了解的是這之中是否還有不同的角度，能夠有一個施力點，也就是這些人是因為在他們的經驗過程中找到這樣一條路(邊界、職責)從而理出世界運行的一套規律，那我能否也從自己過往的經驗也理出另一套不一樣的規則呢? 我想了一下，我人生經驗中對於”過去塑造現在”這件事其實滿相信的，除非”痛到不行不然不會改變”，也就是”痛”是一個引爆點，我人生的某個痛，會再既有邏輯的作用下不斷增長，直到一個臨界點，他爆發了，才會發生改變，但變完又是下一個痛再蓄勢待發。 所以我從而發現我人生再走一個迴圈，每次似乎都有變好，但每次也都是痛苦的，這樣的人生理解，對應到軟體開發上，我認為本質邏輯是一致的，目標都是解決問題，只是方法跟形式。 我體認到現在聊的這些職責跟邊界某種程度是為了穩定而去扼殺變化性，我人生的那種方式是從不穩定去得到變化性，或許這就是一種好設計是因人而異的吧?
